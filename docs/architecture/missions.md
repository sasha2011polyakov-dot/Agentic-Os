# Поручения: выполнение технических заданий на естественном языке (раздел 28 ТЗ)

Статус: принято · Дата: 2026-10-12

## 1. Термины
- **Поручение** (mission) — задание пользователя на естественном языке и весь процесс его выполнения: анализ, исследование, стратегия, план, выполнение, проверка, исправление, итог. Раздел UI — «Поручения».
- **Задача** (task) — элемент трекера (раздел «Задачи»). Поручение может создавать задачи, но это разные сущности.
- **Набор изменений** (change set) — предложенные агентом изменения файлов (создание, замена содержимого, удаление) с diff. Пока набор не применён, на диске ничего не меняется.

## 2. Почему не фиксированный конвейер
Конвейер ТЗ из раздела 10 — фиксированный граф из 8 агентов. Поручения адаптивны: агент-аналитик определяет **тип и сложность** задачи и **какие этапы реально нужны** (`needs`). Движок исполняет только их:

| Сложность | Этапы | Агенты |
|---|---|---|
| simple | анализ → выполнение → проверка → итог | аналитик, исполнитель, проверяющий |
| moderate | + изучение проекта, + план | + исследователь проекта, планировщик |
| complex | + исследование (локальное и веб), + сравнение вариантов, + независимое ревью | + исследователь, архитектор решений, ревьюер |

Тип задачи (`research`, `design`, `implementation`, `bugfix`, `improvement`, `documentation`, `spec`, `other`) влияет на роли исполнителей подзадач и на набор проверок, но не ограничивает план: планировщик может собрать любой план из доступных ролей и инструментов.

## 3. Жизненный цикл (машина состояний)

```
draft → analyzing → (needs_input ⇄ analyzing) → researching → planning → awaiting_approval → ready → executing ⇄ paused
                                                                                              ↓
                                     needs_fix ← verifying ← ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘
                                         ↓            ↓
                                     executing    completed | partially_completed | failed
любой незавершённый → cancelled;  любой активный → needs_input (нужен ответ, доступ или модель)
```
Переходы валидируются таблицей допустимых переходов (`missions/state.ts`). Каждый переход записывается в журнал поручения с причиной.

Режимы:
- **«Исследовать и спланировать»** (`plan`): анализ → контекст → исследование → стратегия → план → итог. Изменений нет, кроме сохранения отчёта, если пользователь это разрешил.
- **«Выполнить»** (`execute`): полный цикл. Рискованные действия (применение наборов изменений к проектам, запуск команд проверки, изменение существующих документов) требуют подтверждения по политике поручения.

## 4. Модель данных (system.db)
`missions` (task_id, title, original_request, normalized — JSON внутреннего ТЗ, system_id, scope, mode, status, priority, assumptions, constraints, acceptance_criteria, plan, selected_strategy, policy, totals, error, timestamps), `mission_steps` (этап или подзадача: роль, агент, вход и выход, статус, попытки, ключ идемпотентности), `mission_events` (журнал действий), `mission_messages` (обсуждение), `change_sets` и `change_set_files` (предложенные изменения, статус применения, хеши до и после, снапшоты для отката), `mission_checks` (результаты проверок по критериям и команд). Исходный запрос хранится отдельно от нормализованных требований (сравнение «не исказила ли система смысл»).

## 5. Исполнение действий
- Агенты действуют **только через инструменты**. Инструменты поручений: всё из раздела 9 плюс `propose_file_change` (добавить файл в набор изменений), `run_check` (запустить проверку проекта по имени), `create_document`, `create_agent_definition` (новый агент как черновик в системе — включается только пользователем).
- `propose_file_change` никогда не пишет на диск. Применение набора изменений — отдельная операция с проверкой конфликтов (хеш файла на момент предложения), снапшотом прежнего содержимого в истории системы, журналом и откатом.
- Разрешение `projects.write` на проект (выдаётся пользователем в карточке проекта) позволяет применять наборы изменений к этому проекту. Без него набор можно только просмотреть и скачать как patch.
- `run_check` выполняет **только команды, заданные пользователем** в настройках проекта (`checks`: имя, программа, аргументы). Запуск через `execFile` без shell, с тайм-аутом, ограниченным выводом и очищенным окружением (без секретов). Требует разрешения `commands.run` и подтверждения запуска в поручении.

## 6. Проверка и честность результата
- Каждый критерий готовности получает статус `met | partially_met | not_met | unverifiable | not_applicable` с доказательством: результат проверки, путь к артефакту, цитата.
- Итог `completed` возможен, только если все применимые критерии `met`. Иначе `partially_completed` (часть выполнена) или `failed`. Выполненные и невыполненные проверки перечисляются явно.
- Повторные утверждения агентов не считаются независимыми, если опираются на один и тот же источник: проверяющий получает доказательства с их источниками, а детерминированный валидатор считает число **различных** источников для ключевых выводов.

## 7. Вмешательство пользователя
Пауза, продолжение, отмена; дополнительное требование (план помечается устаревшим, планировщик получает выполненные шаги и сохраняет их, если нет конфликта); запрет инструмента (`policy.deniedTools` — исполнитель отклоняет вызовы); «исследовать ещё вариант»; «выбрать другой вариант» (стратегия заменяется, зависимые шаги пересчитываются); повтор неудачного этапа; вопрос в обсуждении (отвечает агент-консультант, только на чтение).

## 8. Восстановление после сбоя
Шаги со статусом `running` при старте переводятся в `pending`, а поручение — в `paused` с пометкой «восстановлено после перезапуска». Шаги с побочными эффектами (применённые наборы изменений, созданные документы) имеют ключ идемпотентности и не выполняются повторно.
