# Поручения: выполнение технических заданий на естественном языке (раздел 28 ТЗ)

Статус: реализовано · Обновлено: 2026-10-14 · Код: `packages/core/src/missions/*` · Тесты: `packages/core/test/missions.test.ts` (21 сценарий, включая 15 сценариев приёмки 28.17), `apps/server/test/api.test.ts` (HTTP).

## 1. Термины

- **Поручение** (mission): задание пользователя на естественном языке и весь процесс его выполнения. Раздел UI называется «Поручения», ключ поручения имеет вид `M-001`.
- **Задача** (task): элемент трекера в разделе «Задачи». Это другая сущность.
- **Этап** (phase): стадия алгоритма 28.5 — анализ, контекст, исследование, стратегия, план, выполнение, проверка, исправление, ревью, итог.
- **Шаг** (mission step): запись о работе одного агента. Шаги бывают двух видов: этапные (например, «Разбор запроса») и шаги плана (`S1`, `S2`, … и `FIX1`).
- **Набор изменений** (change set): предложенные изменения файлов. У поручения один накопительный набор (`changeGroup = mission:<id>`). До решения пользователя в исходном проекте ничего не меняется (раздел 29).

## 3. Адаптивный алгоритм (28.5)

```
analysis → [context] → [research] → [strategy] → planning → execution → verification ⇄ fix → [review] → summary
                                                    └── режим plan: planning → summary
```

Этапы в скобках выполняются, только когда они нужны. Решение принимается кодом (`nextPhase`) по внутреннему ТЗ от агента-аналитика:

| Этап | Когда выполняется |
|---|---|
| context | Задача про проект (`project_exploration` или тип implementation, bugfix, improvement) и в области есть проекты. Либо нужно локальное исследование, указаны документы или выбраны другие системы. Для области «только общедоступные источники» не выполняется. |
| research | `web_research`, область `public` или вложена ссылка. Если веб-доступ запрещён, этап не выполняется, а в итоге появляется ограничение. |
| strategy | `alternatives`, сложность `complex` или тип `design`. |
| review | `independent_review` или сложность `complex`. |

Простая задача проходит путь «анализ → план → выполнение → проверка → итог» силами 3–4 агентов. Фиксированной цепочки из десятков агентов нет (28.6).

### 3.1. Этапы

1. **Анализ.** Агент `mission-analyst` превращает свободный текст во внутреннее ТЗ: тип, результат, требования, ограничения, критерии, риски, вопросы, сложность, нужные этапы.
   - Исходный запрос хранится отдельно и дословно (`original_request`).
   - Блокирующий вопрос без допущения переводит поручение в «Требуется вмешательство» с конкретным вопросом.
   - Неблокирующий вопрос становится явным допущением.
   - Раундов вопросов не больше трёх. Если ответа так и не было, это записывается как ограничение.
2. **Контекст.** Работают `project-explorer` и `researcher`, параллельно в пределах `maxParallel`.
   - Цитаты свидетельств проверяются кодом. Неподтверждённое утверждение становится допущением.
   - Для области «несколько систем» сначала выполняется детерминированный поиск по выбранным системам. У каждого результата сохраняется `systemId`.
3. **Исследование.** Работает `web-researcher`. Цитаты сверяются с сохранённым текстом загруженных страниц и подсчитываются независимые домены.
4. **Стратегия.** `solution-architect` формирует варианты: reuse, configure, library, extend, new, combined.
   - Если нужно подтверждение, появляется вопрос `strategy`.
   - Выбор пользователя (`selectedBy: user`) сохраняется при пересчёте.
5. **План.** Работает `mission-planner`.
   - План проверяет `validatePlan`. При ошибках планировщику даётся одна попытка исправить план с указанием ошибок.
   - Если требования изменились во время работы планировщика, план составляется заново для новой ревизии.
   - Строка `Конфликт: …` в заметках планировщика превращается в вопрос `conflict` (28.13).
   - Подтверждение плана зависит от политики `approvePlan`:
     - `always` — подтверждается всегда;
     - `risky` (по умолчанию) — при шаге с высоким риском, высоком риске от аналитика или проверках проекта, которые ещё не разрешены;
     - `never` — не запрашивается.
6. **Выполнение.**
   - Шаги запускаются по зависимостям. Независимые шаги идут параллельно до `maxParallel`.
   - Шаги `implementer`, меняющие файлы, идут строго по одному.
   - Шаги роли `verifier` закрываются этапом «Проверка».
   - Ответ агента о действии, которое не подтверждено вызовом инструмента, не засчитывается и записывается как ограничение («не имитируй выполнение»).
7. **Проверка.** Каждый запуск этапа получает собственный маркер (`verification:<round>:<id>`), поэтому результаты разных запусков не смешиваются. Порядок:
   - валидаторы: изменения только в области поручения; исходные проекты не менялись во время выполнения (базовый слепок хешей);
   - разрешённые команды проверки в рабочей копии с текущим содержимым набора;
   - ревью безопасности изменений;
   - агент `verifier`;
   - страж критериев.
8. **Исправление.** Цикл ограничен `maxFixRounds`, по умолчанию 2. Он запускается только для того, что изменение может исправить: упавшие проверки, критерии `not_met`, серьёзные дефекты. Ограничения среды он не трогает: «проверки не запускались», «изменения только предложены».
9. **Независимое ревью.** Работает `independent-reviewer`. Он сверяет результат с исходным текстом запроса и ищет искажения смысла.
10. **Итог.**
    - Статус вычисляется по критериям и доказательствам (`finalStatus`).
    - Сохраняется не больше одного отчёта. При пересчёте он обновляется на месте.
    - Если документ уже подготовил документатор, отдельный отчёт не создаётся.
    - Если источник разрешает применение, поручение задаёт вопрос `apply_changes`.

## 4. Честность результата (28.16)

`guardCriteria` не принимает «выполнено» от агента без доказательств:

- `met` без доказательства становится `unverifiable`;
- `check_command`: упавшая проверка даёт `not_met`; если проверки не запускались, получается `unverifiable` с перечислением причин;
- `artifact_exists` без артефакта даёт `not_met`;
- `source_verification` без подтверждённой цитаты даёт `unverifiable`; единственный независимый веб-источник даёт `partially_met`;
- `manual` подтверждает только пользователь (`confirmCriterion`);
- если изменения только предложены и не применены ни к рабочей копии, ни к проекту, оценка понижается до `partially_met`.

Итоговые статусы:

- `completed` — все применимые критерии выполнены и нет проваленных этапов;
- `partially_completed` — что-то достигнуто;
- `failed` — ничего не достигнуто.

В режиме plan с ограничениями итог — `partially_completed`.

## 5. Модель данных (system.db)

- **`missions`.** Хранит:
  - исходный запрос и вложения;
  - `normalized` (внутреннее ТЗ) и `revision`;
  - режим, статус, этап, приоритет;
  - область, политику, лимиты;
  - контекст, исследование, варианты, стратегию, план и `plan_stale`;
  - критерии, дополнительные требования, разрешённые проверки;
  - базовый слепок, ограничения, текущий вопрос (`pending`), счётчик циклов исправления;
  - результаты ревью, итог, `report_doc_id`, расход, ошибку, причину статуса и время.
- **`mission_steps`.** Хранит фазу, шаг плана, роль, агента, вход и выход, статус, попытки, `idempotency_key`, `side_effects` (что шаг уже сделал: инструмент, цель, ссылка) и время.
- **`mission_events`** — журнал действий (28.12.6). **`mission_messages`** — обсуждение, ответы на вопросы, решения, замечания.
- **`mission_checks`** — команды, валидаторы и критерии по раундам.
- **`change_sets`** (`mission_id`) — накопительный набор изменений поручения.

## 6. Агенты, модели и бюджет

- Агент запускается только через `AgentRuntime`: схемы, конверт недоверенного контента, контролируемый исполнитель инструментов.
- Область запуска (`RunScope`) задаёт пользователь: проекты, документы, системы, веб, запреты инструментов, разрешённые проверки, `missionId`, `changeGroup`.
  - Объект области «живой»: запрет инструмента действует и на уже идущие шаги.
  - Для области `public` запрещены все инструменты чтения и изменения локальных данных.
- Идемпотентность. Ключ этапного шага: `mission:phase:role:planStep:r<revision>:f<fixRound>:<variant>`. Завершённый шаг с тем же ключом не выполняется повторно, используется сохранённый результат.
- Запасная модель (28.15). При ошибке модели (`MODEL_UNAVAILABLE`, `STRUCTURED_OUTPUT_FAILED`, `PROVIDER_*`, `CONTEXT_TOO_LARGE`) движок пробует до двух **других локальных** моделей. На облако он автоматически не переключается: облачные провайдеры в список запасных не попадают.
- Ошибки, которые пользователь может устранить, переводят поручение в «Требуется вмешательство» с конкретным вопросом:
  - `model` — модель, ключ, сеть;
  - `budget` — лимит;
  - `setup_agents` — агенты.
- `RunBudget` поручения: лимиты вызовов, токенов и стоимости. Расход сохраняется в `missions.totals`.

## 7. Вмешательство пользователя (28.13)

| Действие | API (`/api/systems/:systemId/missions/:mid/...`) | Поведение |
|---|---|---|
| Пауза / продолжить / отмена | `pause`, `resume`, `cancel` | Пауза: идущие шаги завершаются, новые не начинаются, курсор этапа сдвигается без продолжения работы. Отмена: шаги отменяются, результаты сохраняются. |
| Решение по вопросу | `decide` | Принимаются только действия, допустимые для этого вида вопроса. Устаревший `pendingId` отклоняется. |
| Добавить требование, критерий, ограничение | `requirements` | `revision++`, план помечается устаревшим. На ближайшей безопасной границе он пересчитывается. Выполненные шаги с `keep_existing` сохраняются, невыполненные заменяются. Если требование конфликтует с прежним, появляется вопрос `conflict`. |
| Уточнить критерии | `PUT criteria` | Неизменённые критерии сохраняют статус. Для новых критериев проверка повторяется. |
| Изменить план | `PUT plan` | Тот же `validatePlan`, что и для планировщика. |
| Исследовать ещё вариант | `options` | Стратегия пересчитывается, затем план. |
| Выбрать другой способ | `strategy` | `selectedBy: user`, план пересчитывается. |
| Запретить инструмент | `deny-tool` | Действует сразу, записывается в журнал безопасности. |
| Повторить этап или фазу | `steps/:sid/retry`, `phases/:phase/retry` | Повтор шага плана или всей фазы (новая ревизия). |
| Подтвердить ручной критерий | `criteria/:cid/confirm` | Итог завершённого поручения пересчитывается. |
| Обсуждение | `discuss`, `messages/:msg/apply` | Консультант отвечает по состоянию поручения. Его предложения применяются только кнопкой пользователя. |
| Лимиты, название, предпроверка, агенты | `PUT limits`, `PUT title`, `POST missions/preflight`, `POST missions/setup-agents` | Предпроверка показывает агентов, маршрут моделей (локальная или облачная), разрешения, режимы проектов и проверки. |

## 8. Связь с защитой проектов (раздел 29)

- Агент только **предлагает** изменения (`propose_file_change`). Из-за `changeGroup` все предложения поручения попадают в один набор.
- Режим проекта меняет только пользователь:
  - «Только изучение»: предложения невозможны, это записывается как ограничение;
  - «Подготовить изменения»: набор есть, но рабочей копии нет и проверки не запускаются (честно отражено в критериях);
  - «Работать в копии»: проверки выполняются в рабочей копии, исходный проект не меняется;
  - «Применить к исходному проекту»: в конце поручение задаёт вопрос `apply_changes`.
- Решение `apply` проходит по шагам: просмотр именно того содержимого, которое видел пользователь (иначе `REVIEW_STALE`), → проверки в рабочей копии → все ворота `ChangeSetService.apply` (риски с явным подтверждением, проверенная резервная копия).
- Инструмент `run_check` внутри поручения сначала синхронизирует рабочую копию с текущим набором (`syncMissionWorkCopy`).

## 9. Восстановление (28.11)

- Корректное закрытие системы. Драйвер прерывается. Шаги без побочных эффектов возвращаются в `pending`. Шаги исполнителя, а также шаги с записанными `side_effects`, помечаются `failed` с пояснением «автоматически не повторяется». Поручение переходит в «Приостановлена».
- Аварийное завершение. При следующем запуске `start()` делает то же самое для поручений в рабочих статусах.
- «Продолжить». Прерванные шаги с побочными эффектами превращаются в вопрос `error`: «повторить или пропустить». Остальное продолжается. Завершённые этапы повторно не выполняются (идемпотентность).

## 10. Межсистемная работа (28.14)

- Область поручения бывает четырёх видов: `system`, `projects`, `systems` (явно выбранные другие системы) и `public`.
- Агенты читают другие системы только при разрешении `systems.read` и только выбранные системы.
- Свидетельства проверяются в системе-источнике, `systemId` сохраняется в `sourceReferences`.
- Результаты (документы, отчёт) сохраняются в системе, где создано поручение. Другие системы не изменяются (тест 14).

## 11. Ограничения (честно)

- Качество анализа, плана и изменений зависит от модели. Небольшие локальные модели могут не справиться со структурированным выводом. Тогда движок пробует другую локальную модель, а если не выйдет, спрашивает пользователя.
- Конфликт требований распознаётся по маркеру `Конфликт:` в заметках планировщика, то есть зависит от модели. Детерминированного семантического детектора противоречий нет.
- Изоляция проверок зависит от наличия bubblewrap (раздел 29, §10.7). Без него режим «ограниченный», и итог поручения прямо об этом сообщает.
- Параллельность ограничена `maxParallel` (1–6). Изменения файлов выполняются последовательно.
